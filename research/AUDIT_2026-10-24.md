# Independent review and corrections — 2026-10-24

Scope: static GitHub source review, verification against primary dataset/paper sources, and small isolated pandas checks. No full checked-out repository CI run or real Yambda experiment was carried out in this review; do **not** treat source inspection as end-to-end validation.

## Completed (source-backed)

- **High: wrong positive definition.** Earlier implementation used `played_ratio_pct >= 30`, an arbitrary threshold while official Yambda Listen+ is **strictly greater than 50%**. Unified the label predicate between snapshot construction and evaluation and added boundary tests at 50/51%. Dataset: https://huggingface.co/datasets/yandex/yambda
- **High: missing indirect connections.** The original claim that Yambda lacks usable artist/album relations was incorrect: standalone `artist_item_mapping.parquet` and `album_item_mapping.parquet` exist, as described by the dataset authors. Added optional history-only user–artist and user–album affinities (4 manual features + 8 automated features) while retaining a working listens-only mode. Original paper: https://arxiv.org/abs/2505.22238
- **Medium: held-out test touched too early.** Popularity test score was computed before the feature subset selection. Moved test scoring of *all* four rankers after all feature choices.
- **Medium: inconsistent history requirement.** Manual baseline used a 90-day window while earliest training split only required 60 days of history; standardized manual maximum to 60 days to match the guard.
- **Medium: no feature-computation cost breakdown.** Added candidate retrieval, manual, generated, relation-stage wall clock fields for each snapshot and totals across snapshots. CatBoost training time already includes all automatic subset trials.
- **Medium: missing boundary and indirect-link tests.** Added tests for 50/51%, target-window exclusivity, unchanged results after appending later events, multiple artists per item, no future lookahead in artist/album aggregation, and synthetic end-to-end relation mode.
- **Documentation:** Corrected original methodology, acknowledged related published temporal engineering, changed workflow to opt-in metadata download for research, retained explicit non-official offline evaluation.

## Known limitations — do not call the project finished

1. **P0: No measured real-data outcome.** The full repository pytest suite has not been executed here; no true Yambda-50M model scores have been measured or independently confirmed. Run manual-only Actions unit/smoke first, then the manual Yambda research workflow and inspect artifacts/logs.
2. **P0: Retrieval ceiling.** Candidate generation remains only global popularity + user repeats + local observed transitions. A strong recommender baseline should compare ItemKNN and ideally ALS/BPR retrieval; measure candidate Recall, new-item coverage and hit fraction before boosting.
3. **P1: Weakness of the baseline.** 27 manual features with metadata are more meaningful, but still do not contain collaborative score/latent-factor features; experiment must not call this competitive with the state of the art without evidence.
4. **P1: Limited feature-search scope.** Importance ranking + choosing 4/8/12/all of 29 features is an automated *selection baseline*, not optimal continuous search or a learned time-decay model. A follow-on study should compare decay-only vs count-only, search decay scales and relation types within a fixed budget.
5. **P1: Exposure confounding.** Yambda has `is_organic` and other event types. Without impressions, unavailable tracks cannot be treated as explicit dislikes. Report and test different organic/recommendation-induced slices, with identical protocol per model.
6. **P1: No intervals or multi-seed stability.** Add per-user bootstrap confidence intervals and repeat experiments across full-history sampled user cohorts (100, 1,000, 10,000 users), with seeds and sample lists persisted.
7. **P1: Memory/computation bottlenecks.** Repeated pandas joins of artist/album lookup tables onto all historical interactions and repeated group-bys for each snapshot are likely expensive and may OOM on full Yambda-50M; profile 100/1,000 users first. Streaming or pre-aggregated engines (DuckDB/Polars) may be warranted.
8. **P2: Test-horizon sensitivity.** The protocol currently tests on only a final global one-day horizon; this may coincide with atypical behavior. Use repeated rolling validation / independent backtests; do not retune using the final test.
9. **P2: Candidate evaluation and language.** NDCG/Recall use *all* future listened tracks in denominator (including missed retrieval); users with zero positives are excluded from macro-average. Scores cannot be compared to Yambda's official benchmark directly, because the target, candidate generation and cutoff differ.
