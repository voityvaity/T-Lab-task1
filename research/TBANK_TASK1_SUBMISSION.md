## 1. Постановка задачи

Исследовательский вопрос: **может ли алгоритмически созданный и выбранный набор временных признаков конкурировать с ручными признаками CatBoost при одинаковой истории взаимодействий, одинаковом временном разбиении и одинаковых кандидатах?**

В качестве конкретной задачи выбрано **персональное ранжирование треков по вероятности качественного прослушивания в следующие сутки**. Использован открытый [Yandex Yambda-50M](https://huggingface.co/datasets/yandex/yambda), содержащий около 46,5 млн прослушиваний и историю 10 000 пользователей. В полном исходном датасете есть и другие типы событий, но данная реализация намеренно использует **только `listens.parquet`** и статические отображения трек–исполнитель / трек–альбом.

Для пары пользователь–трек в момент `t` целевая переменная равна 1, если в интервале `[t, t + 1 день)` было хотя бы одно прослушивание строго **более 50% трека** (`played_ratio_pct > 50`), иначе 0 для кандидата. Это собственная задача ранжирования, а не официальный протокол соревнования Yambda. **Ноль не означает доказанный отказ:** в данных нет логов показов каждому пользователю всех кандидатов.

**Основная метрика:** NDCG@10, дополнительная — Recall@10. Диагностически считаются кандидатные ROC-AUC и LogLoss (не CTR, не метрики на истинно показанных отрицательных объектах).

## 2. Данные и защита от утечки

Используются `uid`, `item_id`, `timestamp`, `played_ratio_pct`; статические `artist_item_mapping.parquet` и `album_item_mapping.parquet` позволяют посчитать косвенные интересы к исполнителю и альбому. Временные метки Yambda указаны **в пятисекундных интервалах**, а не в Unix-секундах.

- Подвыборка формируется **по случайным идентификаторам пользователей, без усечения их историй**. В эксперименте ниже выбраны 100 пользователей с `seed=42`.
- Используется **общий глобальный временной якорь полного файла**: `26000000` пятисекундных интервалов. Поэтому момент тестирования не зависит от того, у какого пользователя в выборке случилось последнее событие.
- Четыре обучающих среза: `25740800`, `25792640`, `25844480`, `25896320`; валидация: `25948160`, тест: `25982720`.
- Интервалы целевых событий **не пересекаются**. Для всех источников кандидатов, ручных/сгенерированных признаков и ItemKNN допустима только история с `timestamp < cutoff`.
- Ранжировщики на каждом срезе сравниваются на **одном и том же** списке кандидатов; недоступные кандидаты будущие позитивы не подмешиваются.
- Выбор размера автоматически отобранного поднабора происходит **по NDCG@10 на валидации**. Для итогового основного сравнения название модели тоже выбирается **до доступа к тестовым оценкам**.

Версия датасета зафиксирована: `e8b04458db77e2fb30a24e65f78923fa48b7d297`. В `run_config.json` сохранены зависимости, гиперпараметры, время и SHA-256 идентификаторов выбранной когорты. Программные регрессионные тесты проверяют чувствительность к будущим событиям, границы label, сохранение истории, уникальность признаков и работу синтетического пайплайна.

## 3. Подходы

### 3.1. Кандидаты

Для каждого пользователя генерируется **до 200 треков** из объединения трёх исторических источников:
1. популярные треки в выборке пользователей;
2. недавние уникальные прослушивания этого пользователя;
3. треки, встречавшиеся в исторических переходах за последние 14 дней, с интервалом не более одного часа.

После удаления дублей свободные места заполняются исторически популярными треками. Это **не** полный каталог и **не** кандидатный ALS / полноценный ItemKNN retrieval. Покрытие кандидатов измеряется отдельно. Оно ограничивает достижимые Recall и NDCG независимо от качества CatBoost.

### 3.2. Ручной CatBoost

23 заранее заданных признака: счётчики активностей пользователя, трека и пары в фиксированных окнах `1/7/30/60` дней; давность взаимодействия; разнообразие прослушиваний; средний процент воспроизведения; тренд `7/30`; склонность к популярности. Ещё четыре признака — интерес пользователя к **исполнителям и альбомам** за `7/30` дней. Один дополнительный признак — оценка ItemKNN на прошлом совместном прослушивании (итого **28 входных признаков** в режиме с метаданными).

Обучается `CatBoostClassifier` с `depth=6`, `learning_rate=0.06`, `iterations=120`, `loss_function=Logloss`. Для сопоставимости у обучаемых CatBoost-вариантов одинаковые основные гиперпараметры.

### 3.3. Алгоритмическая генерация и отбор

Генератор программно перечисляет комбинации:
- область агрегирования: **пользователь / трек / пара пользователь–трек**;
- счётчики в окнах `1, 3, 7, 10, 14, 30, 60` дней;
- экспоненциальные затухания с масштабами `2, 5, 7, 10, 21, 30` дней;
- косвенные интересы пользователь–исполнитель и пользователь–альбом в окнах `1, 3, 14, 60` дней.

Всего **47 автоматически генерируемых сигналов** в режиме с метаданными. Часть их названий/значений совпадает с ручным набором; при объединении дубликаты столбцов удаляются. `CatBoost` сначала ранжирует признаки по важности **на обучении**. Далее по валидации выбирается размер ведущего поднабора из `4/8/12/20/32/47` и переобучается соответствующая модель.

Это **простая алгоритмическая автоматизация ограниченного поиска**, а не LLM-агент, не универсальный AutoML и не новая теория экспоненциального затухания.

### 3.4. Дополнительные сравнения

Включены популярность, отдельно ItemKNN (на общем наборе кандидатов), ручной CatBoost, выбранный автоматический CatBoost, их объединение, `counts-only` и `decays-only`. Все модели сравниваются на одинаковых кандидатах и временных срезах.

## 4. Результаты на настоящих данных: текущий SHA

**Подтверждённый источник измерений:** [Actions #40180827590](https://github.com/voityvaity/T-Lab-task1/actions/runs/40180827590) и архив `yambda-research-report` (GitHub artifact ID `12593793737`); `100` пользователей, `120` итераций, seed `42`. Важно: **в тестовом дне лишь 14 пользователей с положительными действиями**. Поэтому выводы предварительные, даже несмотря на корректное исполнение эксперимента.

| Модель | Валидация NDCG@10 | Тест NDCG@10 | Тест Recall@10 |
|---|---:|---:|---:|
| Популярность | 0.02413 | 0.03812 | 0.03345 |
| ItemKNN | 0.03489 | 0.10229 | 0.09751 |
| **Ручной CatBoost** | 0.11957 | **0.20056** | **0.24915** |
| Автоматически выбранные признаки | 0.11365 | 0.18056 | 0.23710 |
| Ручные + автоматические | 0.10909 | 0.19791 | 0.24405 |
| **Только автоматически сгенерированные счётчики** | **0.13393** | 0.16123 | 0.21230 |
| Только затухающие признаки | 0.11279 | 0.18618 | 0.23611 |

**Модель, выбранная строго по валидации:** `auto_counts_only` (валидация `0.13393`). Её тестовый NDCG@10 = **`0.16123`**. На тесте ручной CatBoost оказался лучше (`0.20056`), но выбирать его по этому факту задним числом было бы некорректно.

**Что получилось:** автоматический подбор создал работоспособный и заметно лучший популярности ранжировщик, но **превосходство над сильным ручным бустингом не доказано**. На маленькой выборке лучший вариант по валидации оказался далеко не лучшим на тесте. Это указывает на возможные вариации качества между днями и недостаточную устойчивость выбора признаков.

### 4.1. Значимость различий

Для автоматической модели относительно ручной: `ΔNDCG@10 = −0.02000`. Доверительный интервал методом парного bootstrap пользователей (1 000 выборок) **`[−0.08010; +0.02219]`**, то есть включает ноль.

Для объединённой модели: `ΔNDCG@10 = −0.00265` и интервал `[−0.04640; +0.03850]`. С этими данными **нет достаточного основания утверждать ни преимущество, ни ухудшение**. Эти интервалы описывают только вариацию тестовых пользователей, не времён или других когорт.

### 4.2. Какие признаки отобрал алгоритм

Автоматический отбор выбрал **8 признаков**:
`user_count_7d`, `pair_decay_10d`, `user_count_30d`, `user_decay_10d`, `user_decay_7d`, `user_decay_21d`, `pair_decay_30d`, `user_decay_30d`.

Шесть из восьми — экспоненциально затухающие агрегаты. При этом `counts-only` победил на валидации: одного анализа важности отдельных признаков **недостаточно**, чтобы гарантировать преимущество составленной модели.

### 4.3. Покрытие и затраты

- Валидация: **57 из 318** будущих положительных пар вошли в кандидаты (**17.92%**).
- Тест: **33 из 116** будущих положительных пар вошли в кандидаты (**28.45%**).
- Общий расчёт признаков для шести временных срезов: **34.5 с**, из них **32.1 с** — косвенные признаки исполнитель/альбом, **0.77 с** — автоматически генерируемые признаки, **0.41 с** — ручные, **0.29 с** — ItemKNN, **0.88 с** — подбор кандидатов.
- Обучение ручного CatBoost: около **0.8 с**; автоматический поиск признаков со всеми предварительными подгонками и пробами: **4.5 с**. Сравнение по времени должно включать расходы на **весь** поиск признаков, а не только окончательный fit.
- Сам эксперимент занял **46.6 с** и использовал примерно **1.66 ГиБ** максимальной оперативной памяти; время настройки окружения и скачивания данных отдельно.

**Основной практический узкий участок:** поиск кандидатов, затем затраты на косвенные связи.

### 4.4. Диагностические ROC-AUC и LogLoss

В тесте кандидатный ROC-AUC ручной модели `0.79845`, автоматической `0.83953`. Кандидатный LogLoss соответственно `0.00926` и `0.00970`. Эти показатели нельзя интерпретировать как качество CTR на реальных показах; доля отмеченных положительных пар мала, а отрицательные — лишь ненаблюдаемые кандидаты.

## 6. Интерпретация, ограничения и следующий опыт

**Вывод исследования на текущем этапе:** алгоритмическая генерация временных агрегатов может заменить часть ручной работы и построить конкурентоспособный базовый ранжировщик на одном датасете. Однако по имеющимся проверкам **она не обошла ручной CatBoost достоверно**. Наибольшую ценность дали объективное сравнение временных окон, изоляция затухающей и счётной статистики, учёт дорогих косвенных связей и диагностика ограничений отбора по валидации.

Главные ограничения:

1. **Ненаблюдаемые негативы и смещение показов.** Отсутствующее прослушивание — не факт, что пользователь увидел или отклонил трек.
2. **Кандидатный потолок:** ~28% покрытия в тесте. Даже идеальный ранжировщик не сможет извлечь отсутствующие треки.
3. **Малая мощность теста:** только 14 положительных пользователей, широкие доверительные интервалы.
4. **Один тестовый временной отрезок:** не доказывает переносимость на другие дни или популяции.
5. **Ограниченный генератор:** перебирает фиксированные области/окна/затухания, но пока не изобретает произвольные JOIN и новые типы статистик.
6. **Функции и доступная информация:** ручная модель получает ItemKNN-признак, автоматическая — нет. Это допустимое сравнение с более сильным ручным baseline, однако для анализа эффекта **именно** генерации признаков в будущем следует провести отдельную абляцию «с общим ItemKNN у обеих моделей».
7. **Версия 1 000 пользователей не совпадает с текущей 100-пользовательской по составу признаков**. Нужен эксперимент на 1 000 пользователях актуального SHA.

**Следующий строго определённый опыт:** повторить тот же актуальный SHA на 1 000 пользователях; сохранить значения NDCG/Recall, интервалы, покрытие и затраты. Затем провести несколько временных окон/случайных выборок и отдельное сравнение с общим ItemKNN-признаком. Расширение кандидатов через ItemKNN/ALS имеет смысл как самостоятельный этап, но при этом для сравнения ранжировщиков необходимо снова удерживать их кандидатный набор одинаковым. Улучшения после просмотра теста требуют нового нетронутого holdout для окончательных выводов.

## 7. Воспроизведение

Для локального запуска требуется Python >=3.11:

```bash
python -m pip install -e ".[dev]"
pytest -q

# Минимальная проверка — синтетические данные; не используются в выводах
python -m tlab.experiment --demo --users 8 --snapshots 1 --candidates 24 --iterations 10 --output results/smoke

# Публичные данные — скачиваются только при необходимости
python -m tlab.data download --output data --with-metadata

# Реальный Yambda-50M на 100 пользователей
python -m tlab.experiment --data data/flat/50m/listens.parquet --users 100 --seed 42 --iterations 120 --metadata-dir data --output results/yambda-100

# Масштабирование до 1000 пользователей
python -m tlab.experiment --data data/flat/50m/listens.parquet --users 1000 --seed 42 --iterations 120 --metadata-dir data --output results/yambda-1000
```

Для GitHub Actions: [Manual tests](https://github.com/voityvaity/T-Lab-task1/actions/workflows/manual-tests.yml) и [Manual Yambda research](https://github.com/voityvaity/T-Lab-task1/actions/workflows/manual-yambda-research.yml).
