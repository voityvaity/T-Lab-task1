## 1. Постановка задачи

Исследовательский вопрос: **может ли алгоритмически созданный и выбранный набор временных признаков конкурировать с ручными признаками CatBoost при одинаковой истории взаимодействий, одинаковом временном разбиении и одинаковых кандидатах?**

В качестве конкретной задачи выбрано **персональное ранжирование треков по вероятности качественного прослушивания в следующие сутки**. Использован открытый [Yandex Yambda-50M](https://huggingface.co/datasets/yandex/yambda), содержащий около 46,5 млн прослушиваний и историю 10 000 пользователей. В полном исходном датасете есть и другие типы событий, но данная реализация намеренно использует **только `listens.parquet`** и статические отображения трек–исполнитель / трек–альбом.

Для пары пользователь–трек в момент `t` целевая переменная равна 1, если в интервале `[t, t + 1 день)` было хотя бы одно прослушивание строго **более 50% трека** (`played_ratio_pct > 50`), иначе 0 для кандидата. Это собственная задача ранжирования, а не официальный протокол соревнования Yambda. **Ноль не означает доказанный отказ:** в данных нет логов показов каждому пользователю всех кандидатов.

**Основная метрика:** NDCG@10, дополнительная — Recall@10. Диагностически считаются кандидатные ROC-AUC и LogLoss (не CTR, не метрики на истинно показанных отрицательных объектах).

## 2. Данные и защита от утечки

Используются `uid`, `item_id`, `timestamp`, `played_ratio_pct`; статические `artist_item_mapping.parquet` и `album_item_mapping.parquet` позволяют посчитать косвенные интересы к исполнителю и альбому. Временные метки Yambda указаны **в пятисекундных интервалах**, а не в Unix-секундах.

- Подвыборка формируется **по случайным идентификаторам пользователей, без усечения их историй**. В эксперименте ниже выбраны 100 пользователей с `seed=42`.
- Используется **общий глобальный временной якорь полного файла**: `26000000` пятисекундных интервалов. Поэтому момент тестирования не зависит от того, у какого пользователя в выборке случилось последнее событие.
- Четыре обучающих среза: `25740800`, `25792640`, `25844480`, `25896320`; валидация: `25948160`, тест: `25982720`.
- Интервалы целевых событий **не пересекаются**. Для всех источников кандидатов, ручных/сгенерированных признаков и ItemKNN допустима только история с `timestamp < cutoff`.
- Ранжировщики на каждом срезе сравниваются на **одном и том же** списке кандидатов; недоступные кандидаты будущие позитивы не подмешиваются.
- Выбор размера автоматически отобранного поднабора происходит **по NDCG@10 на валидации**. Для итогового основного сравнения название модели тоже выбирается **до доступа к тестовым оценкам**.

Версия датасета зафиксирована: `e8b04458db77e2fb30a24e65f78923fa48b7d297`. В `run_config.json` сохранены зависимости, гиперпараметры, время и SHA-256 идентификаторов выбранной когорты. Программные регрессионные тесты проверяют чувствительность к будущим событиям, границы label, сохранение истории, уникальность признаков и работу синтетического пайплайна.

## 3. Подходы

### 3.1. Кандидаты

Для каждого пользователя генерируется **до 200 треков** из объединения трёх исторических источников:
1. популярные треки в выборке пользователей;
2. недавние уникальные прослушивания этого пользователя;
3. треки, встречавшиеся в исторических переходах за последние 14 дней, с интервалом не более одного часа.

После удаления дублей свободные места заполняются исторически популярными треками. Это **не** полный каталог и **не** кандидатный ALS / полноценный ItemKNN retrieval. Покрытие кандидатов измеряется отдельно. Оно ограничивает достижимые Recall и NDCG независимо от качества CatBoost.

### 3.2. Ручной CatBoost

23 заранее заданных признака: счётчики активностей пользователя, трека и пары в фиксированных окнах `1/7/30/60` дней; давность взаимодействия; разнообразие прослушиваний; средний процент воспроизведения; тренд `7/30`; склонность к популярности. Ещё четыре признака — интерес пользователя к **исполнителям и альбомам** за `7/30` дней. Один дополнительный признак — оценка ItemKNN на прошлом совместном прослушивании (итого **28 входных признаков** в режиме с метаданными).

Обучается `CatBoostClassifier` с `depth=6`, `learning_rate=0.06`, `iterations=120`, `loss_function=Logloss`. Для сопоставимости у обучаемых CatBoost-вариантов одинаковые основные гиперпараметры.

### 3.3. Алгоритмическая генерация и отбор

Генератор программно перечисляет комбинации:
- область агрегирования: **пользователь / трек / пара пользователь–трек**;
- счётчики в окнах `1, 3, 7, 10, 14, 30, 60` дней;
- экспоненциальные затухания с масштабами `2, 5, 7, 10, 21, 30` дней;
- косвенные интересы пользователь–исполнитель и пользователь–альбом в окнах `1, 3, 14, 60` дней.

Всего **47 автоматически генерируемых сигналов** в режиме с метаданными. Часть их названий/значений совпадает с ручным набором; при объединении дубликаты столбцов удаляются. `CatBoost` сначала ранжирует признаки по важности **на обучении**. Далее по валидации выбирается размер ведущего поднабора из `4/8/12/20/32/47` и переобучается соответствующая модель.

Это **простая алгоритмическая автоматизация ограниченного поиска**, а не LLM-агент, не универсальный AutoML и не новая теория экспоненциального затухания.

### 3.4. Дополнительные сравнения

Включены популярность, отдельно ItemKNN (на общем наборе кандидатов), ручной CatBoost, выбранный автоматический CatBoost, их объединение, `counts-only` и `decays-only`. Все модели сравниваются на одинаковых кандидатах и временных срезах.

### 4.1. Что было выбрано без просмотра теста

**Основной моделью по наилучшей валидационной NDCG@10 (0.16691) выбрана `auto_decays_only`**, то есть CatBoost только на экспоненциально затухающих статистиках. Её тестовый NDCG@10 = **0.16763**, ручной CatBoost = **0.15819**. Разница `+0.00944`, или **+5.97% относительно ручного** по NDCG@10 в одном тестовом срезе.

Объединение ручных и автоматически выбранных сигналов имеет наиболее высокий *описательный* тестовый NDCG@10 = `0.16774`. **Нельзя объявлять его победителем задним числом**, потому что на валидации он уступал заранее выбранной модели.

### 4.2. Статистическая неопределённость

В модели `auto` (отбор поднабора 47 признаков) тестовый NDCG@10 = `0.16695`, против `0.15819` у ручной: разница `+0.00875` с 95% парным bootstrap-интервалом **[−0.00637; +0.02677]**. У объединённой модели разница `+0.00955` с интервалом **[−0.00139; +0.02393]**. Оба интервала содержат ноль. Поэтому **статистически подтверждённого превосходства на данном протоколе пока нет**.

## 6. Итог исследования и ограничения

**Вывод:** ограниченный алгоритмический поиск по временным окнам и экспоненциальным затуханиям создаёт признаки, позволяющие получить качество **не ниже ручного CatBoost по точечной оценке NDCG@10** на 1 000 пользователях в данном офлайн-протоколе. Заранее выбранная только по валидации decay-only модель дала `0.16763` против `0.15819`. Однако **статистически надёжное преимущество не доказано**; результаты 100 и 1 000 пользователей свидетельствуют о зависимости выбора моделей от размера выборки. Это аккуратный исследовательский результат, а не универсальная победа над ручными признаками.

Сильные стороны: воспроизводимый CatBoost baseline, генератор 47 временных и косвенных признаков, защита от будущих событий, честный одинаковый набор кандидатов, отбор по валидации, семь контролируемых сравнений, полные журналы затрат и анализ причин отрицательных результатов.

Ограничения:
1. Набор кандидатов покрывает **лишь 21.06%** будущих положительных user–item пар в тесте; нельзя делать выводы о ранжировании всего каталога.
2. Ноль у ненаблюдаемого трека — не подтверждённый отказ, поэтому возникает смещение офлайн-метрик.
3. Ручная модель получает ItemKNN-score, а автоматическая — нет: это уместно как сильный baseline, но не является изолированным сравнением генератора при абсолютно одинаковых входных признаках.
4. Отбор 47 признаков ограничен заданными разработчиком окнами, операциями и связями. Это автоматизация перебора и валидационной селекции, **не ИИ-агент, не универсальная автоматическая изобретательность и не новый алгоритм затухания**.
5. Испытания на 1 000 пользователей используют одну когорту и один итоговый день, а тестовый результат уже изучен во время развития проекта. Для подтверждающего вывода нужен новый независимый holdout.
6. Полноценные ALS/ItemKNN **retrieval** и последовательные нейросетевые системы не сравнивались по этому протоколу; нельзя заявлять о превосходстве над ними или над внешними leaderboard.
7. Стоимость автоматического подбора (35.1 с обучения против 6.1 с ручного baseline) выше, несмотря на приемлемое время исполнения на данном объёме.

**Рекомендованное развитие:** (а) оценить на другом отложенном дне и с несколькими seed; (б) построить общее для моделей расширенное candidate retrieval, например ItemKNN/ALS, и повторить честное сравнение; (в) проверить общие и раздельные CatBoost-признаки при одинаковых ресурсах; (г) измерить масштабирование и интервал разницы именно validation-selected `auto_decays_only`.

Победа над ручным бустингом по заданию **не обязательна**. Научная ценность данного отчёта — чёткое исследование автоматизации, сопоставимый baseline, реальные измерения и разбор неопределённости.

## 6.2. Заключительная проверка на трёх временных срезах — выполнена

**Подробное исследование с первичными числами, парными доверительными интервалами, двумя новыми ItemKNN-абляциями и затраченными ресурсами опубликовано отдельно:** [«Временная устойчивость»](TEMPORAL_RESULTS_2026-10-25.md).

Первичный GitHub Actions [#40190598585](https://github.com/voityvaity/T-Lab-task1/actions/runs/40190598585), SHA `97bcb0c63a8677186dc4723f25f00d853cf6a67a`: **26 тестов пройдено**, три реальных отдельных времени, 1 000 пользователей с **полными** историями (`seed=42`), все архивы и диагностические оценки сохранены. Протокол был [зафиксирован до запуска](TEMPORAL_VALIDATION_PROTOCOL.md).

| Лаг тестового дня | Модель, победившая **по валидации** | Тест NDCG@10 выбранной | Ручной CatBoost NDCG@10 | Auto-selected NDCG@10 | Только decay NDCG@10 |
|---:|---|---:|---:|---:|---:|
| 0 дней | `auto_decays_only` | **0.16763** | 0.15819 | 0.16695 | 0.16763 |
| 21 день | `manual` | **0.16309** | 0.16309 | 0.16262 | 0.15834 |
| 42 дня | `auto_counts_only` | 0.16909 | **0.17565** | 0.17982 | 0.18001 |

**Результат:** единый победитель не сохраняется между датами. Особенно важно, что на срезе 42 дня назад автоматические признаки получают высокий тестовый балл, но **победившая по валидации** count-only модель уступает ручной на тесте. Нельзя задним числом заменить выбранную модель на самый высокий тестовый результат.

95%-е **парные** bootstrap-интервалы для `auto − manual`: на лаге 0 `[−0.00637; +0.02677]`, на лаге 21 `[−0.01001; +0.00951]`, на лаге 42 `[−0.00620; +0.01518]`. **Каждый включает ноль.** Поэтому устойчивое и статистически доказанное превосходство не продемонстрировано.

### 6.2.1. Контроль равной доступности ItemKNN

Две дополнительные модели позволяют сравнить исходные ручную и автоматическую модели **каждую с одним и тем же ItemKNN-score и без него**. На датах 0/21/42:

- Ручной CatBoost с ItemKNN минус без ItemKNN по тестовой NDCG@10: `−0.00150 / +0.00070 / −0.00393`.
- Автоматический CatBoost с ItemKNN минус без ItemKNN: `+0.00075 / −0.00581 / −0.00480`.

Все соответствующие 95%-е пользовательские интервалы включают ноль. **ItemKNN не даёт стабильного прироста**; это устраняет одно важное смешение факторов, но не превращает наблюдения в причинный эксперимент. Контрольные модели не участвуют в выборе победителя основных семи вариантов.

### 6.2.2. Стоимость и границы вывода

Общий эксперимент: **9 мин 56.75 с**, пик памяти **3.36 ГиБ**, покрытие положительных кандидатов **21.06% / 19.63% / 23.36%** по трём датам. За три временных среза генерация признаков потребовала **92.103 + 88.018 + 87.763 с**; большая часть — соединения с таблицами исполнителей и альбомов.

**Ограничения:** эти даты разделены, но используется *одна когорта* и частично пересекающиеся исторические данные; первый тестовый день изучался ещё до заключительного опыта; в Yambda отсутствуют подтверждённые логи экспонирования негативных кандидатов. Полный подбор параметров и генерация новых кандидатов на этих же тестах ради максимального балла были бы методологически некорректны.

**Итог для преподавателя:** гипотеза автоматического поиска признаков проверена в нескольких временных условиях; результат воспроизводим, неоднозначность честно объяснена, а дополнительные модели прояснили вклад ItemKNN. **Победа над ручным бустингом в условии не обязательна.**

## 7. Воспроизведение

Для локального запуска требуется Python >=3.11:

```bash
python -m pip install -e ".[dev]"
pytest -q

# Минимальная проверка — синтетические данные; не используются в выводах
python -m tlab.experiment --demo --users 8 --snapshots 1 --candidates 24 --iterations 10 --output results/smoke

# Публичные данные — скачиваются только при необходимости
python -m tlab.data download --output data --with-metadata

# Реальный Yambda-50M на 100 пользователей
python -m tlab.experiment --data data/flat/50m/listens.parquet --users 100 --seed 42 --iterations 120 --metadata-dir data --output results/yambda-100

# Масштабирование до 1000 пользователей
python -m tlab.experiment --data data/flat/50m/listens.parquet --users 1000 --seed 42 --iterations 120 --metadata-dir data --output results/yambda-1000
```

Для GitHub Actions: [Manual tests](https://github.com/voityvaity/T-Lab-task1/actions/workflows/manual-tests.yml) и [Manual Yambda research](https://github.com/voityvaity/T-Lab-task1/actions/workflows/manual-yambda-research.yml). Оба запускаются **только вручную**. Во втором workflow сначала исполняются `pytest` и синтетический end-to-end, затем скачивание Yambda, реальное обучение и загрузка артефакта `yambda-research-report`.

Эксперимент сохраняет `REPORT.md`, `metrics.json`, `feature_selection.json`, `run_config.json`. Не следует заменять реальные данные синтетическими при формулировании конкурсного вывода.
