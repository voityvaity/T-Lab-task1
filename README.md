# Автоматизация временных признаков в рекомендательной системе

**Исследование для задания №1 Академии Т-Банка.** Реализованы сильный ручной baseline на CatBoost, программная генерация временных признаков, экспериментальное сравнение с контролем времени и кандидатов, а также анализ качества и вычислительных затрат.

**[Полный конкурсный отчёт](research/TBANK_TASK1_SUBMISSION.md)** · **[Краткий ответ для преподавателя](research/FOR_REVIEWER_RU.md)** · **[Проверка на трёх датах](research/TEMPORAL_RESULTS_2026-10-25.md)**

## Главный результат

Автоматически сформированные признаки **могут конкурировать** с ручными признаками CatBoost, но **статистически надёжный и устойчивый выигрыш не установлен**. На трёх временных срезах лучшая модель, выбранная **по валидации**, меняется. По условию задания это содержательный исследовательский результат; победа над бустингом не обязательна.

| Тестовый срез | Выбор по валидации (из 7 моделей) | Тест NDCG@10 выбранной | Тест NDCG@10 ручного CatBoost | Тест NDCG@10 авто-признаков |
|---|---|---:|---:|---:|
| Последний день (лаг 0) | Только экспоненциальное затухание | **0.16763** | 0.15819 | 0.16695 |
| 21 день раньше | Ручной CatBoost | **0.16309** | 0.16309 | 0.16262 |
| 42 дня раньше | Только счётчики | 0.16909 | **0.17565** | 0.17982 |

**Источник:** [успешный GitHub Actions #40190598585](https://github.com/voityvaity/T-Lab-task1/actions/runs/40190598585), код `97bcb0c63a8677186dc4723f25f00d853cf6a67a`, [первичный ZIP с отдельными метриками всех трёх дат](https://github.com/voityvaity/T-Lab-task1/actions/runs/40190598585/artifacts/12598361548). Все **26 тестов** и два синтетических этапа проверки пройдены. Выборка — **1 000 случайных пользователей с полными историями** (seed 42); тесты используют **одну и ту же когорту** на разных датах.

95%-е парные bootstrap-интервалы разницы `auto − manual`:
- лаг 0: `+0.00875` [−0.00637; +0.02677];
- лаг 21: `−0.00046` [−0.01001; +0.00951];
- лаг 42: `+0.00417` [−0.00620; +0.01518].

Все интервалы включают ноль. Это **не доказанное превосходство**. Bootstrap здесь измеряет неопределённость по пользователям внутри даты, не по будущим дням.

## Как устроен эксперимент

**Данные и задача.** [Yandex Yambda-50M](https://huggingface.co/datasets/yandex/yambda); используем `listens.parquet` и статические отображения трек–исполнитель/альбом. Для пары `user–item` прогнозируем, будет ли прослушано **строго больше 50% трека** в следующие сутки. Непрослушанный трек считается *ненаблюдаемым*, но **не подтверждённым отказом**. Это собственная офлайн-задача, а не официальный лидерборд Yambda.

**Поиск кандидатов.** На каждого пользователя — до 200 исторически доступных треков: популярность, недавние повторы и переходы. **Одинаковые кандидаты** оцениваются всеми моделями. Покрытие будущих позитивов на трёх тестовых датах: **21.06%, 19.63% и 23.36%** — главный ограничивающий фактор.

**Ручной CatBoost.** 23 заранее определённых прямых/статистических признака, 4 косвенных интереса к исполнителю и альбому, 1 ItemKNN-score (28 входных сигналов). `CatBoostClassifier`: глубина 6, learning rate 0.06, 120 итераций. Дополнительные baseline: популярность и отдельный ItemKNN.

**Автоматизация.** Программное перечисление **47 признаков**: счётчики `user/item/user–item` на окнах 1/3/7/10/14/30/60 дней, экспоненциальные затухания на масштабах 2/5/7/10/21/30 дней и интересы к исполнителю/альбому. Важности определяются по **обучению**, количество выбранных признаков (4/8/12/20/32/все) — по **валидации**. Дополнительно сравниваются только счётчики, только затухание и их объединение с ручными признаками. Это **алгоритмический ограниченный поиск**, а не ИИ-агент.

**Защита от утечек.** История пользователя сохраняется полностью; для признаков, кандидатов и ItemKNN используются только события `timestamp < cutoff`. Все train/validation/test-срезы и их целевые окна разделены во времени; для разных тестовых дат сдвигается **весь** план обучения и оценки. Победитель выбирается по validation NDCG@10, а не по тесту. Сравниваются NDCG@10 и Recall@10, дополнительно candidate-conditional ROC-AUC/LogLoss, парные интервалы и стоимость.

## Отдельная абляция ItemKNN

Проверено, что происходит при удалении ItemKNN из ручной модели и при добавлении такого же сигнала к автоматически выбранным признакам. **Стабильного улучшения нет**: на некоторых датах сигнал помогает, на других ухудшает NDCG. Контрольные модели не участвовали в выборе победителя исходного семимодельного сравнения. Числа и интервалы — в [подробном анализе](research/TEMPORAL_RESULTS_2026-10-25.md).

## Стоимость и ограничения

Заключительный прогон на трёх датах: **9 мин 56.75 с** вычисления, пик **3.36 ГиБ RAM**. Наиболее затратны расчёты косвенных интересов (связи с исполнителями и альбомами). Помимо трёх дат, выполнена проверка на другой когорте из 1 000 пользователей (`seed=137`): [Actions #40188496986](https://github.com/voityvaity/T-Lab-task1/actions/runs/40188496986). У неё победитель на валидации тоже изменился.

Основные ограничения: небольшое покрытие кандидатов; отсутствие подтверждённых экспозиций/негативных примеров; частично пересекающиеся исторические данные между датами; ранее просмотренный тестовый день (лаг 0); ограниченное пространство автоматически генерируемых признаков; отсутствие сопоставимого официальному протоколу ALS/SASRec. Поэтому **не заявляем SOTA, инновационную формулу затухания или доказанное превосходство над работами других авторов**.

## Воспроизведение

Python 3.11+:

```bash
python -m pip install -e ".[dev]"
pytest -q

# Полные события выбранных пользователей и статические справочники
python -m tlab.data download --output data --with-metadata

# Те же три тестовых среза и ItemKNN-абляции
python -m tlab.robustness \
  --data data/flat/50m/listens.parquet \
  --metadata-dir data --users 1000 --seed 42 \
  --lags 0,21,42 --iterations 120 --snapshots 4 \
  --candidates 200 --threads 4 --output results/temporal
```

Без локального компьютера запустить [Manual Yambda research](https://github.com/voityvaity/T-Lab-task1/actions/workflows/manual-yambda-research.yml) на ветке `main`: `evaluation_mode=temporal_0_21_42`, `users=1000`, `seed=42`, `iterations=120`. Workflow **только ручной**, автоматически запускает тесты и синтетические проверки до загрузки данных, затем сохраняет `TEMPORAL_REPORT.md`, `temporal_robustness.json` и каталоги `lag-0`, `lag-21`, `lag-42`.

Примечание: фактические опубликованные значения принадлежат коммиту `97bcb0c...`. При повторном запуске на новой версии зависимостей могут отличаться численные подробности — исходный `run_config.json` сохраняет установленные версии.
